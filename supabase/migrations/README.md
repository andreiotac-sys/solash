# Proposed safety migrations

These SQL files are **not applied to production**. Run only after comparing the live schema with the proposal, taking a fresh native backup, and rehearsing on a fully isolated clone. Production execution requires explicit owner approval.

The actual public catalog was read on 2026-10-16 and is structurally compatible; see `docs/audit/PRODUCTION_SCHEMA_COMPATIBILITY.md`. A reconstructed public-schema fixture passed installation and runtime tests on PostgreSQL 17.6. This fixture is not a native backup or a full Supabase clone. The booking migration now takes ShareRowExclusive before preflight to close an installation race; the FK and RLS migrations also take AccessExclusive locks. Schedule a maintenance window.

All three filenames share the CLI version prefix `20261015`. Do **not** use `supabase db push` or alphabetical ordering for these files. Follow the explicit atomic → client FK → appointment RLS order in the deployment runbook, using separately reviewed transactions.

1. `20261015_atomic_booking_guard.sql` first requires NOT NULL date, time, duration, and status columns, and parses active legacy durations to reject an existing interval crossing midnight. It serializes active writes per calendar date and rejects new overlaps with SQLSTATE `23P01`. Cancelled rows do not block. Personal blocks stored as appointments do block. Exact seconds are compared; unexpected NULL statuses in existing rows are treated as active. Existing historical overlaps are preserved, including active-only status changes on those rows. The trigger requires `READ COMMITTED`; other isolation levels fail closed. Working-hours overrides remain an application decision and never bypass a real overlap. The final file passed an isolated synthetic overnight-preflight test and the 17-case SQL harness; it still needs a faithful production-schema clone before approval.
2. `20261015_protect_client_history.sql` changes the expected `appointments.client_id` foreign key from `ON DELETE CASCADE` to `ON DELETE RESTRICT`. It aborts if the live constraint does not match the expected columns and semantics. A client with appointment history cannot be deleted, including when all appointments were cancelled.
3. `20261015_protect_appointment_history.sql` replaces the broad authenticated DELETE policy with one limited to rows whose `service` is `Blocaj personal`. This preserves intentional deletion of personal blocks while denying accidental direct deletion of customer appointments through authenticated REST/API calls. The service field remains editable by authenticated users, so this policy does not defend against a malicious user who deliberately relabels a customer appointment. It must be applied after the client FK migration. Administrative `service_role` operations retain RLS bypass.

Recheck live constraints, statuses, duration formats, overlaps, RLS, grants, functions, and deletion paths immediately before applying. The 2026-10-16 live inspection found 13 overlap pairs across 11 dates, no invalid durations or active overnight intervals, and confirmed that `appointments.notes` is absent despite checked-in `schema.sql`. An exclusion constraint cannot be added unchanged. Each migration uses a five-second lock timeout; review lock duration and rollout timing with the owner.

Rollback of the booking guard in an isolated environment is `drop trigger solash_prevent_booking_overlap_trigger on public.appointments; drop function public.solash_prevent_booking_overlap(); drop function public.solash_guard_duration_minutes(text);`. Reverting `RESTRICT` to `CASCADE` or restoring the broad appointment DELETE policy would reintroduce data-loss risk and is not a routine production rollback. Frontend rollback is independent of these migrations. See `docs/audit/MIGRATION_READINESS.md` for exact recovery SQL and test evidence.
