## Architecture and feature map

`src/app/page.tsx` contains the six-tab app, all forms, calendar views, reports, local storage, offline queue, WhatsApp, and push controls in one 6,400-line client component. `src/lib/supabase.ts` exposes only the publishable client key. Service role access is limited to server route handlers through `src/lib/push-server.ts`. `src/app/api` contains backup, ICS, and push routes. The PWA uses `public/sw.js` and `src/app/manifest.ts`. The code reads all customer, appointment, and service rows in pages for the app; calendars and reports are computed client-side. Working hours, days off, WhatsApp template, demo cache, and offline queue live in browser `localStorage` and are not shared between devices or captured by cloud backups.

The following feature paths were inspected in source: dashboard and next slot; daily timeline; monthly picker; form, free-slot and long-press creation; editing, drag, and move; cancellation; client search/history and deletion; services; working hours, breaks and days off; legal holidays; personal blocks; reports; WhatsApp links/templates; push subscriptions and reminders; PWA; ICS feed; and backups. Source inspection establishes code behavior, not full production workflow correctness.

## Performance and reliability notes

The app fetches all rows and computes calendars/reports on the client; current appointment count is 3,870. This is a clear scaling pressure, but no profiler or production timing trace was available, so no performance claim is made. Several route handlers, including ICS and push reminder reads, do not page their results. Next.js uses Webpack successfully in this Mac checkout; default Turbopack build fails because native SWC bindings are missing. The service worker only handles push and notification clicks, so no broad offline cache behavior was observed in `public/sw.js`. Preview branch deployment may inherit production Supabase values; Vercel environment separation must be checked before any push.

## Release gates

1. Obtain a native schema-complete database backup and prove an isolated restore, including auth/policies and settings migration plan.
2. Verify live Supabase RLS, grants, triggers, storage policies, and Vercel preview environment isolation.
3. Test authenticated booking, editing, drag, offline sync, backup, PWA push, and ICS in an isolated environment, plus real iPhone Safari.
4. Resolve dependency advisories and concurrency protection before treating double-booking as solved.
5. Review the branch diff and deploy only after explicit owner approval. No production database schema or policy change is included in this branch.
