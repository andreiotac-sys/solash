## Isolated evidence

The verified snapshot was restored to PostgreSQL 16 with `--network none`, no published ports, and a temporary database filesystem. It held 568 clients and 3,870 appointments, including 13 active overlap pairs on 11 dates. The FK and RLS migration files and the booking migration through its exact-second/NULL revision were applied there. The separate local Supabase test stack had the FK change, the RLS deletion policy, and an earlier version of the booking trigger. The isolated test harness [`db_guards_isolated.py`](../../tests/db_guards_isolated.py) passed **17/17** checks, covering simultaneous conflicting inserts, second-level boundaries, cancelled-slot reuse and reactivation, personal blocks, self-edit, rescheduling, invalid duration, an out-of-hours interval, client deletion with active and cancelled history, an active status change on an existing historical overlap, and authenticated appointment versus personal-block deletion. Synthetic rows were removed; the restored table counts remained 568 and 3,870. Dropping NOT NULL on status in isolation made the booking migration abort during preflight; restoring it allowed installation. Reapplying the FK and RLS migrations to the already protected isolated schema failed during preflight as intended; the counts and policies remained unchanged.

After adding the final active-legacy-duration/overnight preflight, the complete three-file migration set was run in a fresh PostgreSQL 16 container with `--network none` and synthetic rows. A 23:30–00:30 legacy appointment made the atomic migration abort, and the transaction left no guard function installed. After removing that test row, all three files applied and the **final version passed 17/17** isolated SQL checks, including a pre-existing overlap pair. This proves the final SQL on the synthetic schema; it does not replace a rehearsal on a faithful clone of the unknown live DDL and data.

The restored snapshot is a data-only backup, so its RLS and role definitions were reconstructed for this test. The local Supabase stack has the checked-in RLS and Auth stack. A separate local Supabase transaction under `SET ROLE authenticated` confirmed that a customer appointment DELETE affected zero rows and a personal-block DELETE affected one row; the transaction was rolled back. Neither environment proves that the live production policies, grants, functions, triggers, statuses, duration formats, or all foreign keys match. The known repository FKs are `appointments.client_id ON DELETE CASCADE` and `push_appointment_reminders.appointment_id ON DELETE CASCADE`. Direct deletion of an appointment would cascade to its reminder rows; the proposed RLS policy prevents that ordinary authenticated path for customer appointments, while `service_role` can still delete. Inventory the actual live FK graph before approval.

## Required production preflight

1. Obtain a native, schema-complete backup and rehearse its restore in a fully isolated Supabase project. Compare `pg_catalog` constraints, policies, grants, triggers, functions, and Auth/Storage configuration with the proposal. Do not infer the live DDL from the JSON snapshot.
2. Check all appointment statuses, duration strings, timestamp precision, personal-block markers, and 13 known historical overlap pairs. Verify no authenticated DELETE or ALL policy besides the one named in the migration and no SECURITY DEFINER function that bypasses its intent.
3. Review the lock window and a quiet rollout time. Apply one migration at a time to a faithful clone first, then repeat authenticated REST/UI booking, cancellation, customer deletion, and block removal tests. Production execution still requires explicit approval.

## Recovery instructions

An error during any migration rolls its transaction back. Confirm its final schema state before retrying. For the booking guard alone, the exact inverse DDL is:

```sql
begin;
drop trigger solash_prevent_booking_overlap_trigger on public.appointments;
drop function public.solash_prevent_booking_overlap();
drop function public.solash_guard_duration_minutes(text);
commit;
```

This removes atomic overlap protection. For a regression in customer deletion or block removal, first correct the application or narrow policy while keeping `RESTRICT` and history protection. The exact inverse of the FK change would drop `appointments_client_id_fkey` and recreate `foreign key (client_id) references public.clients(id) on delete cascade`; the exact inverse of the RLS change would drop `"Allow authenticated users to delete personal blocks"` and recreate the previous authenticated DELETE policy with `using (true)`. **Both inverses reopen known data-loss paths and must not be run as automatic rollback steps.** They require a fresh native backup, isolated rehearsal, explicit owner approval, and a review of data created since the backup. A frontend flag or Vercel rollback does not reverse database writes or schema changes.
